# 검색 설계

수집 → 병합 → 색인 다음 단계다. 색인 설계는 `index-design.md`를 본다.

## 1. 흐름

```
검색어 + 화면 선택
   │  QueryAnalyzer  (사전: resources/search/query-dictionary.yml)
   ▼
조건(날짜·지역·무료·분류·반경) + 의미 검색 문장
   │
   ├─ 문장이 없다 → Postgres 조회(QueryDSL), 곧 시작하거나 진행 중인 것부터
   └─ 문장이 있다 → 임베딩 → Qdrant 에서 조건 필터를 먼저 걸고 그 안에서 유사도 순
                      → 관련도 하한(min-score) 아래는 버림 → Postgres 에서 행사 정보를 읽어 같은 순서로
```

- **조건은 필터로 먼저 건다.** 벡터 검색으로 상위 N건을 뽑은 뒤 거르면 조건에 맞는 결과가 모자란다. Qdrant 필터(날짜 범위·지역·분류·가격·위경도 반경)를 먼저 적용한 뒤 그 안에서 순위를 매긴다.
- **항상 오늘 이후의 행사만** 나온다(종료일이 오늘 이후). 날짜 표현이 있으면 그 기간과 겹치는 행사.
- **화면에서 고른 값이 검색어 속 표현보다 우선**한다. 검색어 속 표현은 조건으로 쓰이지 않아도 문장에서는 빠진다.
- 응답의 `interpreted` 에 "이렇게 이해했어요"(서울, 이번 주말, 무료…)를 담아 화면에 보여 준다. 잘못 이해했을 때 사용자가 알 수 있다.
- 벡터 검색을 쓸 수 없으면(임베딩 키 없음, Qdrant 장애) 오류 대신 **제목 글자 검색으로 대신하고** 응답의 `degraded` 로 알린다.
- 내 주변: 브라우저 위치(위경도) + 반경. 거리는 하버사인으로 계산해 가까운 순으로 정렬하고 카드에 거리를 보인다.

## 2. 조건 사전 (코드에 표현을 박지 않는다)

`resources/search/query-dictionary.yml`: 날짜 표현(오늘·내일·이번 주말…), 무료 표현, 종류·분류 표현, 지역 이름 뒤 조사, 군더더기 말투. 새 표현은 이 파일에만 추가한다. 시작할 때 사전이 가리키는 날짜 규칙·분류가 실제로 있는지 검사한다. 날짜 규칙의 **계산**만 코드(`DateRule`)에 있고 단위 테스트로 확인한다.

지역은 `taxonomy/regions.csv`와 `region-aliases.yml`을 그대로 쓴다. 시군구 이름이 여러 시도에 있으면(중구·서구) 시도가 함께 언급될 때만 지역으로 본다. 짧은 군더더기("곳", "거")는 다른 낱말 속에서 지워지지 않게 낱말 경계에서만 뺀다.

## 3. 관련도 하한 (측정값)

`text-embedding-3-small`(768차원) 코사인 유사도, 로컬 색인(행사 1,848건) 기준.

| 질의 | 최고 점수 | 비고 |
|---|---|---|
| 클래식 연주회 | 0.46 | 관련 있음 |
| 대학로 연극 | 0.39 | 관련 있음 |
| 비 오는 날 실내 데이트 | 0.39 | 관련 있음 |
| 아이와 (갈 만한 공연) | 0.35 | 관련 있음 |
| asdfasdf | 0.29 | 관련 없음 |
| 양자역학 논문 작성법 | 0.29 | 관련 없음 |

관련 없는 질의의 최고 점수(0.29)가 관련 있는 질의의 낮은 쪽(0.35)과 가까워서 `tshow.search.min-score` 를 **0.30** 으로 시작했다. 여유가 크지 않으므로 평가 세트를 늘려 가며 조정한다. (예: "치킨 맛집"은 0.42로 통과한다 — 과자·요리를 소재로 한 공연이 실제로 있어서 완전히 틀린 결과는 아니다.) 점수는 API 응답의 `score` 로 볼 수 있다(화면에는 보이지 않는다).

## 4. 평가 세트

`src/test/resources/search-eval/cases.yml` + `SearchEvalTest`. 로컬 Postgres·Qdrant 와 임베딩 키가 있을 때 돌린다.

```
RUN_SEARCH_EVAL=true ./gradlew.bat test --tests "*SearchEvalTest*" --no-daemon
```

- 조건 사례: 나온 행사 **모두**가 지역·가격·분류·기간 조건을 지키는지(필터가 새지 않는지).
- 의미 사례: 위쪽 n건 중 기대한 분류·제목 말이 몇 건인지.
- 관련 없는 질의: 결과가 비어야 한다.

검색을 고칠 때는 사례 하나를 맞추는 대신 이 세트 전체의 전후를 비교한다. 현재 10/10 통과.

## 5. API와 화면

- `GET /api/search?q=&kind=&category=&sido=&sigungu=&when=&date=&free=&lat=&lon=&radiusKm=&page=&size=` → `ApiResponse<SearchResponse>`
- `GET /api/events/{id}` → `ApiResponse<EventDetail>`
- 화면: `/`(검색 + 결과), `/events/{id}`(상세). 모든 선택 버튼은 링크라서 자바스크립트 없이도 동작하고, 스크립트는 지역 선택 자동 적용과 "내 주변"(위치 권한)만 한다.
- 상세 화면에는 출처(KOPIS·한국문화정보원·한국관광공사)를 표기하고, 모든 화면 아래에 "일정·요금은 바뀔 수 있다"는 안내를 둔다.
- 이미지는 소스가 준 주소를 그대로 쓰고(`referrerpolicy="no-referrer"`, 지연 로딩), 불러오지 못하면 종류별 아이콘으로 대신한다.

## 6. AI 추천 (Gemini, 버튼을 눌렀을 때만)

일반 검색은 LLM 없이 동작하고, 결과 화면의 "AI 추천 받기" 를 눌렀을 때만 Gemini 를 부른다 (RAG: 검색한 후보를 LLM 이 읽고 고르고 설명).

```
버튼 → /recommend (화면 조각) 또는 /api/recommend (JSON)
  → 같은 검색 파이프라인으로 후보 20건 (조건 필터 + 의미 검색 + 관련도 하한)
  → 후보를 "번호 | 제목 | 분류 | 기간·상태 | 장소 | 가격 | 연령 | 출연 | 소개 90자" 한 줄씩 만들어 Gemini 에 전달
  → Gemini 가 번호(최대 8개)와 한 줄 이유를 JSON 으로 답함 → 후보 밖 번호·중복은 버리고 행사 카드로 바꿔 표시
```

- **환각 방지**: id 대신 번호를 쓰고 후보 밖 번호는 무시한다. 지시문(`prompts/event-curator.st`)은 후보에 적힌 사실만 쓰게 하고, 요청·소개글 속 "지시를 무시하라" 류 문구는 따르지 않게 한다. 맞는 행사가 없으면 비워서 안내한다(관련 없는 후보를 그대로 보여 주지 않는다).
- **실패 대체**: 키 없음·시간 초과(`timeout-seconds`)·오류·엉뚱한 응답이면 오류 대신 검색 순서 그대로 보여 주고 이유를 안내한다. 후보가 없으면 AI 를 부르지 않는다.
- **비용 통제**: 사람(IP)별·서비스 전체 하루 한도, 같은 조건 30분 결과 캐시(캐시 응답은 횟수에 세지 않음, 내 주변은 캐시 안 함), nginx 분당 6번. 입력 토큰은 후보 20건의 짧은 한 줄, 출력 토큰은 최대 8개의 25~40자 이유로 줄였다.
- **설정**: `tshow.recommend.*`(후보 수·최대 선택·시간 초과·한도), 모델은 `spring.ai.google.genai.chat`.
- **실측(로컬)**: 첫 호출 약 2~4초, 같은 조건 재호출 0초(캐시). "이번 주말 서울 아이와 갈 만한 공연" 에서 관람 연령(24개월 이상 등)을 근거로 고른다.
- AI 추천의 품질은 평가 세트에 아직 넣지 않았다(호출 비용·비결정성). 사례를 보며 프롬프트를 고친다.

## 7. 남은 일

- 검색 호출 횟수 제한은 nginx `limit_req` 로 적용함 (`deploy/README.md`). 검색어 길이는 `max-query-length` 로 제한.
- 평가 세트 확대와 점수 하한 재조정, 필요하면 상위 점수 대비 상대 하한 추가.
- 순위 보정(포스터 유무·정보 충실도), 시군구 선택 UI, 박스오피스, AI 추천 품질 점검.
